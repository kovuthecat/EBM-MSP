## T20 — Appliquer l'arbitrage du référent

### Objectif
Reporter dans `CONSTRUIRE-UN-MODULE.md` et dans `DECISIONS.md` ce que le référent a coché dans le
mémo : statut du document, points validés, amendés ou rejetés.

### Pourquoi
La skill de T21 ne peut prescrire que ce qui est arbitré (§11.2). L'arbitrage doit donc être écrit
dans le document qui fait autorité, pas seulement dans un mémo coché. Sinon, la skill et le procédé
divergeraient dès la première lecture.

### Décision clé
- **Premier geste** : le mémo porte une réponse cochée à la question de statut et à chaque point à
  arbitrer. Sinon, `FAIL` nature `environnement` (geste humain préalable manquant), rien d'autre.
- Application **littérale** des cases :
  - validé → le texte reste, et son statut devient « arbitré le AAAA-MM-JJ » ;
  - amendé → le texte suit l'amendement écrit par le référent, mot pour mot ;
  - rejeté → le passage est retiré ou marqué « rejeté », selon ce que dit le mémo.
  - La correction P2 « situations synthétiques » s'applique dans tous les cas (invariant zéro
    donnée patient).
- Une nouvelle ligne dans `DECISIONS.md` (au format du registre) : « statut de
  `CONSTRUIRE-UN-MODULE.md` arbitré », avec renvoi au mémo.

### Lire / Modifier
- Modifier : `docs/decision/CONSTRUIRE-UN-MODULE.md` (en-tête de statut l.1-10 et sections visées
  par les cases), `DECISIONS.md` (une ligne ajoutée).

### Étapes
1. Vérifier les cases du mémo (premier geste).
2. Appliquer chaque case, section par section.
3. Ajouter la ligne de décision.

### Validation
- **N0 auto (bloque le commit)** : `node .claude/workflow/bin/n0.mjs` → exit 0.
- **Tests** : — (document d'autorité, aucune logique).
- **N1 visuel auto** : —
- **N2 humain** : —
- **Anti-raccourci** : un en-tête passé à « arbitré », alors que les points amendés ou rejetés du
  corps sont restés tels quels. La skill lirait alors comme validé ce que le référent a refusé.
  Contrôle : le bilan liste chaque case du mémo avec la ligne du document modifiée en regard.

### Si bloqué
Une case cochée qui contredit une décision du registre : appliquer la case, puisque le référent
arbitre en dernier. Signaler la décision contredite dans la nouvelle ligne de `DECISIONS.md`.

### Message de commit (appliqué par la session elle-même)

## T21 — Skill `construire-module-decision` et ses épreuves

### Objectif
Écrire `.claude/skills/construire-module-decision/`, soit un `SKILL.md` et ses références. Écrire
aussi les huit épreuves de §11.5 sous `docs/commun/epreuves-recherche/cas-module/`, au format du
corpus.

### Pourquoi
Ouvrir un deuxième domaine sans refaire les vagues de correction du DT2 : c'est ce que le procédé
P0→P7 promet, mais seulement si l'ordre, les livrables et les portes sont tenus. La skill les fait
respecter et appelle les circuits au bon moment. Elle sait aussi aiguiller une demande qui n'appelle
pas de module (§11.4). Les épreuves sont écrites ici, avec la skill, et jouées par S12.

### Décision clé
- **Ce que la skill prescrit dépend du statut coché** :
  - procédé arbitré → portes prescriptives ;
  - arbitré en partie → seuls les points validés sont prescrits, le reste est proposé ;
  - reste une proposition → la skill oriente et ne prescrit rien.
  L'autorité reste `CONSTRUIRE-UN-MODULE.md`, et la skill y renvoie section par section, sans
  recopier (§11.5).
- `SKILL.md` porte :
  - les déclencheurs ;
  - la **qualification de la demande** : thème de veille, domaine de décision ou module de nœuds
    (§11.1) ;
  - un **état de chantier unique** : phase, prochaine action, livrables, validations, blocages
    (§11.4) ;
  - les portes, les règles de reprise et de réouverture (§11.4) ;
  - l'appel à `recherche-preuve-triangulee` puis `consolidation.md` en P4, si le mémo l'a accepté.
- Références : gabarits de cadrage, vignettes, bilan des prérequis et clôture (§11.5).
- **Épreuves** (§11.5, huit cas) :
  1. demande ambiguë ;
  2. prérequis générique manquant ;
  3. référent absent pour une attente clinique ;
  4. tentation de lancer OE avant P2 ;
  5. preuve qui contredit une vignette ;
  6. sécurité qui affecte un autre nœud ;
  7. reprise après interruption ;
  8. YAML fidèle mais comportement incorrect.
  Même format que `cas/` : rôle `orchestrateur-module`, Signatures `- (aucune)` admis, et
  `cas-module/README.md` avec sa liste blanche. Celle-ci contient les skills de recherche, la
  nouvelle skill, les agents `*-preuve`, `CLAUDE.md`, `docs/decision/{CONSTRUIRE-UN-MODULE,GRAMMAIRE-NOEUD,00-global}.md`
  et le mémo d'arbitrage. Le harnais lit `--corpus` et `(aucune)` depuis S10/T18.
- `CLAUDE.md` passe de « 4 skills » à 5, avec la nouvelle. `PROJECT_MAP.md` la localise.

### Lire / Modifier
- Créer (nouveaux fichiers) :
  - `.claude/skills/construire-module-decision/SKILL.md` ;
  - `.claude/skills/construire-module-decision/references/*.md` ;
  - `docs/commun/epreuves-recherche/cas-module/README.md` ;
  - `docs/commun/epreuves-recherche/cas-module/M<nn>-<slug>/cas.md`.
- Modifier : `CLAUDE.md` (l.44-49), `PROJECT_MAP.md`.

### Étapes
1. Écrire le `SKILL.md`, puis les références, selon le statut coché.
2. Écrire les huit épreuves. Chaque résultat attendu décrit un **comportement** : aiguiller,
   s'arrêter à la bonne porte, préserver une validation, reprendre au bon endroit. Jamais un contenu
   clinique.
3. Mettre à jour `CLAUDE.md` et `PROJECT_MAP.md`.

### Validation
- **N0 auto (bloque le commit)** : `node .claude/workflow/bin/n0.mjs` → exit 0.
- **Tests** : — (texte de skill et épreuves ; les épreuves sont jouées par S12 sous le harnais).

  attendu : elle aiguille juste, et ne produit aucun contenu clinique à sa place. Le jugement n'est
  pas bloquant ; il se consigne dans le bilan, reversé dans `VALIDATION.md` en fin de plan.
- **Anti-raccourci** : une épreuve dont le résultat attendu se lit dans la skill elle-même (« la
  skill dit X, donc attendu : X ») ne mesure que la relecture. Chaque résultat attendu renvoie à

### Si bloqué

arrêt, et les épreuves portent alors sur l'aiguillage et la reprise, pas sur les portes.
