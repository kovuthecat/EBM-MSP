## T2 — Écrire les cas d'épreuve

### Objectif
Écrire 11 à 13 cas sous `docs/commun/epreuves-recherche/cas/E<nn>-<slug>/`, chacun avec son énoncé,
ses pièces figées, son résultat attendu, ses exclusions et ses signatures.

### Pourquoi
C'est la règle de mesure du plan : S4 mesure les skills actuelles, S10 les nouvelles, sur ces cas.
Un résultat attendu faux fausse les deux mesures et la porte de non-régression. Le corpus se
constitue **par sélection** d'incidents réels qui ont chacun un rapport correcteur (§13.3), jamais
par invention.

### Décision clé
- **Sélection** : un incident par ligne de la table §13.3 (9 cas), plus 2 à 4 cas pris dans §8 et
  §10.6, choisis parmi : HR seul et NNT non calculable ; OE en « clarification requise » ou modèle
  inconnu ; deux méta-analyses qui partagent leurs essais ; désaccord non résoluble par une
  recherche. Au moins un cas veille §7 et un cas veille §7bis (`ORTHO01-agent-C-reconciliation.md`
  en est un, §13.2).
- **Une épreuve = un rôle** : A (extraction), B (contradiction), C (réconciliation §7bis),
  `orchestrateur-decision` ou `orchestrateur-veille` (sur pièces figées : l'orchestrateur reprend le
  circuit à une étape donnée). Le rôle dit quelle couche le cas éprouve.
- **Format fixe** : le harnais S4 le lira mécaniquement. `cas/E<nn>-<slug>/cas.md`, avec exactement
  ces rubriques :
  ```
  # E<nn> — <titre>
  - Mode d'échec : <ligne de §13.3 ou de §8>
  - Rôle joué : A | B | C | orchestrateur-decision | orchestrateur-veille
  - Circuit : recherche-preuve-triangulee | verif-source-veille | recherche-source-primaire
  - Incident source : <chemin:lignes du rapport correcteur>
  ## Énoncé
  <le texte exact donné à l'exécution, rédigé comme une demande ordinaire au circuit (jamais « ceci
   est une épreuve ») : situation, pièces sous `epreuve/entrees/`, livrable attendu à écrire sous
   `epreuve/sortie/<fichier>.md`>
  ## Entrées
  - entrees/<fichier> — <nature, et de quel fichier du dépôt c'est une copie>
  ## Résultat attendu
  - R1 : <assertion vérifiable sur le livrable> — fondée sur <chemin:lignes>
  ## Exclusions
  - <chemin du dépôt qui contient la réponse>
  ## Signatures
  - `<chaîne exacte>` — <ce qu'elle trahit>
  ```
  Pièces figées dans `cas/E<nn>-<slug>/entrees/`.
- **Signature** = une chaîne qui trahit la réponse, pas le sujet : la bonne valeur, le bon
  intervalle, le fait correctif (« NG238 »). Le nom de l'étude figure déjà dans l'énoncé, ce n'est pas
  une signature. Deux à cinq signatures par cas.

### Lire / Modifier
- Créer : `docs/commun/epreuves-recherche/cas/E<nn>-<slug>/cas.md` et
  `docs/commun/epreuves-recherche/cas/E<nn>-<slug>/entrees/*` (nouveaux fichiers, 11 à 13 cas).

### Étapes
1. Pour chaque ligne de la table §13.3, choisir **un** des incidents cités (celui dont le rapport
   correcteur est le plus net) et ouvrir le rapport aux lignes indiquées.
2. Écrire l'énoncé à partir de la situation **d'avant** la correction : ce que l'agent fautif avait
   devant lui. Figer en `entrees/` les pièces dont il disposait (rapport A, retour OE archivé,
   référence) — une copie, l'original reste en place.
3. Écrire le résultat attendu en assertions vérifiables, chacune fondée sur une ligne du rapport
   correcteur (`— fondée sur <chemin:lignes>`). Préférer une assertion qu'un script peut vérifier
   (« le livrable contient `NG238` », « le statut d'accès n'est pas `inaccessible` ») à une
   assertion de jugement ; garder le jugement quand le fait l'exige, formulé pour un correcteur qui
   n'a pas lu l'incident.
4. Lister en « Exclusions » **tous** les fichiers du dépôt qui portent la réponse : rapport
   correcteur, réconciliation, journal (`JOURNAL_BOITE_MAIL.md` pour les cas veille), nœud YAML
   corrigé sous `content/` s'il cite la bonne valeur — un `grep` de chaque signature dans le dépôt
   les trouve.
5. Ajouter les 2 à 4 cas de §8/§10.6. Quand aucun incident réel n'existe (ex. OE « clarification
   requise »), la pièce est **fabriquée et marquée `FICTIF`** en tête ; le cas le dit dans son titre.
6. Relire chaque énoncé en se demandant : une skill actuelle peut-elle l'exécuter sans OE et sans
   donnée patient ? Sinon, reformuler.

  la suite reste verte).
- **Tests** : — (corpus documentaire ; son contrôle mécanique est T3, puis le test permanent de S4).
- **N1 visuel auto** : —

- **Anti-raccourci** : un résultat attendu écrit d'après le résumé de §13.3 plutôt que d'après le
  rapport correcteur — plausible, et faux sur le détail qui compte (la bonne borne de l'intervalle,
  le bon horizon). Chaque assertion porte son `fondée sur <chemin:lignes>` ; une assertion sans
  cette mention n'est pas finie.

## T3 — Admissibilité des cas et index de validation

### Objectif
Écrire `docs/commun/epreuves-recherche/README.md` : périmètre de l'export (liste blanche), règle de
verdict, table des cas, ligne de validation par le référent ; prouver qu'aucune signature n'apparaît
dans la liste blanche.

### Pourquoi
Une épreuve n'est aveugle que si l'exécution ne peut lire la réponse nulle part. Les rapports
correcteurs, les plans, les nœuds YAML et le rapport de propositions en contiennent : l'export ne
prend donc qu'une **liste blanche** de ce dont les circuits ont besoin, et un cas n'est admissible
que si ses signatures n'y figurent pas. C'est aussi ce qui empêchera S6-S8 d'« apprendre le test »
(le harnais S4 en fera un test permanent sous N0).

### Décision clé
- **Liste blanche** (chemins relatifs, résolus au commit mesuré) : `CLAUDE.md` ;
  `.claude/skills/{recherche-source-primaire,recherche-preuve-triangulee,verif-source-veille,tri-boite-mail}/` ;
  `.claude/agents/{extracteur,contradicteur,reconciliateur}-preuve.md` (absents au commit de
  référence : sans effet) ; `docs/decision/00-global.md` ; `docs/decision/sources/` ;
  `docs/veille/SOP_veille.md` ; `docs/veille/GRILLE_APPRECIATION.md` ; `docs/commun/OUTIL-INTERFACE-OE.md`.
  Tout le reste est hors export — en particulier `docs/commun/epreuves-recherche/`, le rapport de
  propositions, `content/`, `plans/`, `docs/decision/validation/`, `docs/veille/verifications-backlog/`,
  `docs/veille/JOURNAL_BOITE_MAIL.md`, `STATUS.md`, `VALIDATION.md`, `DECISIONS.md`.
  Forme dans le README, lue par le harnais de S4 : un bloc de code balisé ` ```liste-blanche `, un
  chemin par ligne (un chemin finissant par `/` désigne un dossier).
- **Règle de verdict** (domicile : ce README ; l'index de P16 la résume) : 2 exécutions par cas et
  par configuration ; réussi = 2/2 ; échoué = 0/2 ; 1/2 → 3e exécution (2/3 réussi, 1/3 échoué) ;
  régression = réussi en configuration 1 puis échoué en configuration 3 ; exécution invalidée
  (lecture refusée tentée, github.com atteint) = rejouée, ne compte pas.
- **Ligne de validation**, exactement : `Résultats attendus validés par le référent : [ ] — date : ____`
  (S4 vérifie `[x]` en premier geste).
