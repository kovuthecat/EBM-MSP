## T-112 — Légende des couleurs d'action, en tête de colonne

### Objectif

Les pastilles d'action colorées livrées en S6 n'ont aujourd'hui aucune clé de lecture. La maquette pose
une légende sticky en tête de la colonne des recommandations.

### Décision clé

La légende de la maquette (l.249-254) liste 4 verbes : Maintenir · Ajouter · Remplacer · Arrêter.
`ActionOption` en compte **5** — `reduire` existe aussi (D35), avec son token `--c-action-reduire`.
La légende doit être **dérivée des verbes réellement présents à l'écran**, pas écrite en dur : sur
`cible-glycemique` ou `statine`, aucune option ne porte de `action` et la légende n'a alors rien à
afficher — elle ne doit pas s'afficher du tout. Rendre une légende fixe de 4 items sur un nœud qui n'en
emploie aucun serait un contresens (et un cas que `banc/` ne couvrira pas).

### Lire / Modifier

- Modifier : `DecisionNodeScreen.tsx` (en-tête de `.decision-node__results-col`) ·
  `DecisionNodeScreen.css`.

### Étapes

1. Dériver la liste des verbes présents : parcourir `vue.familles` → `groupes` → options, collecter les
   `option.action` distincts, dans l'ordre fixe de l'énumération `ActionOption` (pas l'ordre de
   rencontre : la légende doit être stable d'un patient à l'autre).
2. Si la liste est vide → **ne rien rendre**.
3. Sinon, rendre en tête de colonne : le titre de section existant, le nombre d'options réellement
   affichées (cf. T-113 pour le calcul, à partager), et la légende — une puce colorée + le mot par
   verbe, reprenant les tokens `--c-action-*`.
4. L'en-tête devient sticky **à l'intérieur** de la colonne (maquette l.247 : `position: sticky; top: 0`).
   ⚠ La colonne est **elle-même** déjà `position: sticky; top: 72px` au-dessus de 960 px
   (`DecisionNodeScreen.css` l.39-48) : un sticky imbriqué dans un sticky ne se comporte pas comme on
   l'attend. **Vérifier au navigateur**, et si le comportement est faux, laisser l'en-tête non sticky
   plutôt que d'empiler des hacks — la colonne entière suit déjà le défilement.

### Validation

- **N0 auto (bloque le commit)** : `npm test` → aucun échec. Ajouter 2 tests : la légende n'apparaît
  pas sur un nœud sans `action` (`cible-glycemique`) ; elle liste exactement les verbes présents sur
  `prescription`.
- **N1 visuel auto** : `prescription` (légende présente) puis `cible-glycemique` (aucune légende) ;
  vérifier le comportement du sticky imbriqué au défilement. → `/verif-visuelle`
- **N2 humain** : la légende est-elle utile en consultation ou du bruit une fois le code couleur
  appris ? → à consigner dans `VALIDATION.md`.

### Si bloqué

Si le sticky imbriqué produit un en-tête qui saute ou se superpose aux cartes → **STOP** après avoir
essayé la variante non sticky, et signale le comportement observé.

### Message de commit (appliqué en fin de plan)

`feat(decision): légende des couleurs d'action en tête de colonne`

## T-113 — Corriger le compte du CTA flottant mobile

### Objectif

Le bouton « Voir les recommandations (N) » annonce un nombre faux.

### Décision clé

`optionsRenduesCount` (l.309-314) aplatit `vue.familles` **en entier**, y compris les cartes repliées
derrière « Autres pistes possibles (N) » (plafond K5, `lib/replierAffichage.ts`). Le praticien lit donc
un nombre qu'il ne retrouve pas à l'écran. Le nom de la variable dit « rendues » ; le calcul dit
« existantes ». C'est le même défaut de fond que tout le lot 1 de P6 — *ce que l'écran affirme doit être
ce que le calcul croit*.

### Lire / Modifier

- Modifier : `DecisionNodeScreen.tsx` (l.309-314 et l.951-959) · `DecisionNodeScreen.css` (l.73-89).

### Étapes

1. Faire porter le compte sur les options **effectivement visibles sans geste supplémentaire**,
   c'est-à-dire `principales` tel que le calcule déjà `plafonnerPistes(vue)` (utilisé l.778-797) —
   réutiliser cet appel plutôt que d'en refaire un second, sinon les deux divergeront.
2. Partager le même nombre avec l'en-tête de colonne de T-112 : une seule source.
3. Remplacer le `↓` littéral (l.957) par `<Icon nom="fleche-bas" />`.
4. Vérifier que la réserve d'espace `padding-bottom: 140px` en dessous de 960 px
   (`DecisionNodeScreen.css` l.64-68) reste suffisante après la refonte du formulaire de S4 — elle avait
   été calibrée sur une mesure de chevauchement de 33 à 48 px.

### Validation

- **N0 auto (bloque le commit)** : `npm test` → aucun échec. Ajouter 1 test : sur un profil dont les
  options dépassent le plafond K5, le nombre du CTA est **strictement inférieur** au total des familles.
- **N1 visuel auto** : en 375 px de large, sur un profil à plus de 5 options — le nombre du CTA égale le
  nombre de cartes visibles avant le dépli « Autres pistes possibles » ; le CTA ne recouvre pas le
  bouton « Suivant » du formulaire. → `/verif-visuelle`
- **N2 humain** : —

### Si bloqué

Si `plafonnerPistes` ne peut pas être appelée à cet endroit sans réordonner les hooks → **STOP** plutôt
que de dupliquer la logique de plafonnement. Deux calculs du même nombre finiraient par diverger.

### Message de commit (appliqué en fin de plan)

`fix(decision): le CTA mobile comptait les options repliées`

## T-114 — Harmoniser les breakpoints et le fil d'Ariane

### Objectif

Aligner l'écran sur les fondations de S1 et finir la migration des flèches littérales.

### Décision clé

Quatre breakpoints coexistent dans le repo (480/481, 640, 959/960) sans constante partagée, et le seuil
de 960 px est écrit **deux fois** : en CSS (l.31, l.64) et en JS (`matchMedia('(max-width: 959px)')`,
l.287). Ils ne peuvent pas devenir des `var()` — une custom property est interdite dans une `@media`.
La parade est donc documentaire, pas technique : une constante TS exportée pour le JS, et le commentaire
de `tokens.css` (S1) pour le CSS. Ne tente pas d'unifier autrement.

### Lire / Modifier

- Modifier : `DecisionNodeScreen.tsx` (l.286-296, l.530-545) · `DecisionNodeScreen.css`.

### Étapes

1. Extraire le seuil JS dans une constante exportée et commentée (`const LARGEUR_ETROITE_MAX = 959`),
   avec un commentaire renvoyant explicitement aux `@media` de `DecisionNodeScreen.css` l.31 et l.64 :
   les trois valeurs doivent changer ensemble.
2. Remplacer les `←` littéraux du fil d'Ariane (l.535, l.539) par `<Icon nom="chevron-gauche" />`,
   comme la maquette (l.18).
3. Vérifier la tension relevée au cadrage : `.decision-node` est en `max-width: 900px` (l.1-5) alors que
   la grille demande `420 + 380 + 32 = 832 px` minimum. Après la carte compacte de S6, mesurer si la
   colonne de recommandations reste confortable. **Si un élargissement est nécessaire, ne pas le décider
   ici** : mesurer, noter la valeur observée, et le remonter en N2.

### Validation

- **N0 auto (bloque le commit)** : `npm run build` → succès · `npm test` → aucun échec.
- **N1 visuel auto** : bascule à 959/960 px — la grille passe bien à une colonne au même pixel que le
  CTA flottant apparaît (pas de zone où les deux comportements se contredisent). → `/verif-visuelle`
- **N2 humain** : la largeur de 900 px est-elle encore la bonne après la refonte, ou la colonne de
  recommandations gagnerait-elle à s'élargir ? (joindre la mesure de l'étape 3) → `VALIDATION.md`.

### Si bloqué

Si un autre fichier lit le seuil 960 px (grep sur `960` et `959` dans `src/`) → **STOP** et liste-les :
une troisième copie change la nature du correctif.

### Message de commit (appliqué en fin de plan)

`refactor(decision): seuil responsive en constante, fil d'Ariane en SVG`
