## T-032 — Cliquer sur un segment déjà sélectionné le désélectionne

### Objectif

Tout champ `enum` rendu en boutons segmentés doit pouvoir revenir à « non répondu », par le même
mécanisme générique que le champ numérique (`onEffacer`).

### Décision clé

Défaut trouvé par la recette de contrôle P4 (S8) et confirmé par la recette « praticien naïf » : un clic
parasite (souvent provoqué par un reflow de page, cf. `BILAN-P4-2026-07-28.md` §2) pose une valeur
clinique fausse et **définitive** — aucun chemin de code ne ramène un `enum` segmenté à l'état « non
répondu ». Depuis D30, une valeur touchée est *décisive* pour le moteur : ce défaut, tolérable avant,
alourdit désormais chaque clic parasite d'une conséquence clinique réelle. Seule échappatoire actuelle :
« Nouveau patient », qui détruit toute la saisie du patient en cours pour corriger un seul champ.

**Design fixé** : cliquer sur le segment déjà sélectionné (celui pour lequel `aria-pressed="true"`)
appelle `onEffacer(critere.nom)` au lieu de `onChange(critere.nom, valeur)`. C'est la répétition du clic
qui bascule — pas un second élément d'interface. Cohérent avec le pattern « bouton à bascule » déjà
utilisé ailleurs dans l'app, et avec `aria-pressed` qui expose déjà l'état réel pour un lecteur d'écran.

### Lire / Modifier

**Modifier** : `src/features/decision/components/CriteriaForm.tsx`, le rendu du champ segmenté (≈ ligne
375). Le composant reçoit déjà `onEffacer` en prop (optionnel, comme pour le champ numérique — même repli
si absent : ne rien casser chez un appelant qui ne le passerait pas).

### Étapes

1. Dans le rendu du bouton segmenté, calcule si CE bouton est celui actuellement sélectionné (même
   expression que celle déjà utilisée pour `aria-pressed`, ≈ ligne 373 : `touched.has(critere.nom) &&
   String(criteria[critere.nom] ?? '') === valeur`).
2. Si oui **et** `onEffacer` est fourni : `onClick` appelle `onEffacer(critere.nom)`.
3. Sinon (segment non sélectionné, ou `onEffacer` absent) : comportement inchangé, `onChange(critere.nom,
   valeur)`.
4. Vérifie que `handleCriteriaEffacer` (`DecisionNodeScreen.tsx`) produit bien, pour un critère `enum`,
   le même effet que pour un critère `nombre` : retiré de `touched`, `valeurParDefaut` appliquée, plus
   aucune trace de la valeur dans le moteur ni dans l'affichage « à confirmer ». Si `valeurParDefaut`
   (`lib/formLayout.ts`) ne gère pas encore le cas `enum` correctement (ex. retombe sur une chaîne vide au
   lieu d'un état réellement indéterminé) : corrige-le, c'est le même fichier que celui déjà responsable
   de cette fonction pour les autres types.
5. Étends le test de caractérisation existant (ou crée-en un, `CriteriaForm.test.tsx`) : un profil où un
   champ segmenté est répondu, puis re-cliqué → `touched` ne le contient plus, `aria-pressed="false"` sur
   les N boutons, et le critère réapparaît dans les « à confirmer » de l'écran de résultats.
6. Fais tourner la suite complète. Ce changement touche un composant partagé par les six nœuds : les
   régressions attendues sont rares (le comportement de clic sur un segment **non** sélectionné est
   inchangé) — si un test fixait l'ancien comportement (reclic = pas d'effet), corrige l'attente ; si un
   test échoue pour une autre raison, ne l'ajuste pas sans comprendre pourquoi.

### Validation

- Auto (bloque le commit) : le test de l'étape 5 passe · `npm test` → tout vert · `npx tsc --noEmit` →
  0 erreur · `npm run build` → OK.
- Humain (non bloquant, vague de contrôle du plan) : reproduire à l'écran — répondre à un champ segmenté
  sur `Traiter`, re-cliquer sur le même segment, vérifier qu'il redevient « à confirmer » et qu'aucune
  carte ne s'appuie plus sur cette valeur.

### Si bloqué

Si `valeurParDefaut` pour un critère `enum` ne peut pas représenter un état « jamais répondu » distinct
d'une valeur légitime (ambiguïté de type) : STOP, signale le critère concret et le fichier — c'est un
défaut de modélisation plus large que cette tâche, pas un oubli de câblage.
