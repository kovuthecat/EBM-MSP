## T-100 — Clore le plan proprement

### Objectif

L'arbre de travail est commité tâche par tâche, les fichiers de contexte disent l'état réel, et tout
est poussé — une seule fois.

### Décision clé

**Le commit est reporté à la fin, mais il reste atomique par tâche** (`WORKFLOW.md` §4b). Chaque
message de commit est déjà écrit dans le `S<k>.md` de sa tâche : tu ne les rédiges pas, tu les
appliques, avec le staging explicite des seuls fichiers de cette tâche.

**Ordre des commits = ordre des vagues**, pas ordre de `git status`. S0 en premier (le déplacement de
fichiers), puis S1/S2, puis S3, S4, S5, S6/S8, S7. Un historique qui suit l'ordre logique reste
lisible ; un historique qui suit l'ordre alphabétique des chemins ne l'est pas.

**Trois fichiers de contexte disent trois choses différentes** (`WORKFLOW.md` §4a), et les confondre
est le défaut de suivi le plus fréquent :

| fichier | ce qui s'y écrit |
| --- | --- |
| `STATUS.md` | l'**état actuel** : le module Veille existe, deux éditions publiées, ce qui marche et ce qui ne marche pas. Pas l'historique. |
| `TASKS.md` | ce qui **reste** : les lignes PV1 disparaissent, les nouveaux items apparaissent (V3 profil, V4 pour mémoire, première édition live W32, items `concerne_decision` ouverts par S3/S4). |
| `VALIDATION.md` | les jugements **visuels humains en attente** posés par S6, S7 et S8 — rien d'autre. |

**Deux lignes du backlog sont désormais caduques** et doivent disparaître de `TASKS.md` :

- « Onglet **Veille** rend une page blanche (`top: 0` sous nav fixe) » — S6 remplace le placeholder ;
- la ligne « Module Veille : JSON Schema entrée, écran liste filtrable (V1), détail (V2) — zéro code »
  du §« Backlog (Phases suivantes) » — livrée par PV1.

### Lire / Modifier

**Modifier** : `plans/PV1/index.md` (statuts `[x]`), `STATUS.md`, `TASKS.md`, `VALIDATION.md`,
`PROJECT_MAP.md` (la feature `veille` cesse d'être « cible »).

### Étapes

1. Retire `.claude/wave.lock` s'il existe (posé par les vagues parallèles).
2. `git status` et `git diff --stat` : dresse la liste des fichiers par tâche. **Si un fichier n'est
   rattachable à aucune tâche, STOP** et signale-le — c'est soit un oubli, soit une modification non
   planifiée.
3. Commits, dans l'ordre des vagues, avec `git add <fichiers>` explicite et le message écrit dans le
   `S<k>.md` correspondant.
4. `plans/PV1/index.md` : passe chaque session à `[x]`. Une session partiellement faite reste `[ ]`
   avec une note — jamais un `[x]` optimiste.
5. `STATUS.md` : réécris §« Ce qui existe » (le module Veille rejoint Décision), §« Chantier actif »
   (PV1 clos), §« Ce qui casse » (retire la page blanche, ajoute ce que S6/S7 auraient laissé). **80
   lignes maximum**, plafond appliqué par hook.
6. `TASKS.md` : retire les lignes PV1 et les deux caduques ci-dessus ; ajoute les nouveaux items. **60
   lignes maximum.** Si le plafond est franchi, déroule `/purge-contexte` — ne rogne pas au jugé.
7. `PROJECT_MAP.md` : la feature `veille` n'est plus « (cible, non démarrée) » ; l'arborescence reflète
   S0 et S5. **200 lignes maximum.**
8. `VALIDATION.md` : consigne les jugements N2 laissés par S6, S7 et S8. **Rien qu'un navigateur
   puisse constater seul** (`WORKFLOW.md` §6) — si une ligne décrit une erreur console ou un texte
   absent, elle n'a rien à y faire.
9. **Un seul `git push`**, à la fin.

### Validation

- **N0 auto (bloque le push)** : `npm test` → tout vert · `npx tsc --noEmit` → 0 erreur ·
  `npm run build` → OK. Lance-les **avant** le premier commit, pas après le dernier.
- **Vérifiable mécaniquement, bloquant** : `git status` propre après le dernier commit ·
  `STATUS.md` ≤ 80 lignes · `TASKS.md` ≤ 60 · `PROJECT_MAP.md` ≤ 200 · `VALIDATION.md` ≤ 120 ·
  `DECISIONS.md` ≤ 150.
- **N1 visuel auto** : `—` · **N2 humain** : `—`

### Si bloqué

- **Si un test échoue à l'étape N0** : STOP avant tout commit. Ne commite pas « pour ne pas perdre le
  travail » — l'arbre de travail ne se perd pas, et un commit vert est la seule garantie que la
  bissection reste utilisable.
- **Si un plafond de lignes est franchi et que `/purge-contexte` ne suffit pas** : STOP et signale.
  Rogner un fichier de contexte au jugé fait perdre de l'information qui ne vit nulle part ailleurs.
