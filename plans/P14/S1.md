## T-160 — Invariant : inventaire des PAIRES de cartes co-actives (cliquet)

### Objectif

Rendre lisible, et figer, l'information que le golden master contient déjà mais que personne ne peut
lire : **quelles cartes s'affichent ensemble**. Toute paire nouvelle devient un diff à relire.

### Décision clé

Le diagnostic du 2026-08-06 a montré que les faits étaient **déjà** dans
`__snapshots__/caracterisation.prescription.txt` (924 Ko) et `caracterisation.insuline.txt` (620 Ko) :
9 profils y affichent deux cartes titrées « Sulfamide », 2 y affichent « Ne pas sur-titrer » avec
« Titrer la basale ». **La donnée était là, l'agrégation manquait.** Cet invariant est cette agrégation.

Il ne juge rien (comme `caracterisation.test.ts`, et pour la même raison) : il **fige**. Sa valeur est
qu'un fichier de 30 à 210 lignes se relit, alors qu'un fichier de 900 Ko ne se relit pas.

### Lire / Modifier

- Créer : `src/features/decision/engine/banc/paires.test.ts`
- Créer (par exécution) : `src/features/decision/engine/banc/__snapshots__/paires.<id>.txt`, un par nœud.

### Étapes

1. Pour chaque nœud publié (itérer sur `noeuds`, **aucun id en dur** — invariant CLAUDE.md 5), pour
   chaque profil figé du banc : évaluer le nœud et collecter les intitulés des options **`applicable`**
   (jamais `excluded`, `nonRetenues` ni `enAttente`).
2. Agréger sur l'ensemble des profils : l'ensemble des **paires non ordonnées** {A, B} d'intitulés
   co-actifs au moins une fois, avec le **nombre de profils** concernés.
3. Écrire un snapshot **trié par intitulé** (ordre stable, indépendant de l'ordre des profils), une
   ligne par paire : `nb×  A  ⟷  B`. En tête du fichier : le nom du nœud, le nombre de profils, le
   nombre de paires, et **trois lignes de mode d'emploi** disant qu'un diff ici n'est pas une
   régression mais **doit être relu carte par carte** (reprendre la formulation de
   `caracterisation.test.ts`).
4. Ajouter, sous la liste des paires, une **section « paires intra-famille »** : les paires dont les
   deux cartes appartiennent à la même `famille`, en précisant si cette famille est `exclusive`. C'est
   la section qui rend visible une alternative présentée comme cumulable (défaut ③).
5. Vérifier l'ordre de grandeur attendu : ~0 paire pour `cible-glycemique` et `statine` (sortie unique,
   `ordered-first-match`), ~32 pour `insuline`, ~210 pour `prescription`, ~69 et ~147 pour les deux RHD.
   **Un écart franc sur ces ordres de grandeur = STOP** (l'extraction est probablement fausse).

### Validation

- **N0 auto (bloque le commit)** : `npx vitest run src/features/decision/engine/banc/paires.test.ts`
  → 6 snapshots créés, suite verte. Puis `npm run typecheck` → 0 erreur.
- **Contrôle de non-régression du reste du banc** : `npm test` → aucun autre test n'a changé d'état.
- **N1 visuel auto** : — (aucun écran touché)
- **N2 humain** : —

### Si bloqué

Si l'extraction des intitulés depuis le résultat d'`evaluateNode` demande de reproduire le formatage de
`caracterisation.test.ts` : **ne pas parser le snapshot texte**. Réévaluer les nœuds directement

## T-161 — Invariant : deux cartes applicables ne portent jamais le même intitulé

### Objectif

Faire échouer la suite quand un même écran affiche deux cartes de titre identique.

### Décision clé

`prescription` compte 7 intitulés dupliqués (Sulfamide ×3, Metformine / iSGLT2 / AR GLP-1 / Tirzépatide
/ Gliptine / Glinide ×2). C'est **légitime** tant que deux homonymes ne s'affichent pas ensemble — le
nœud sait d'ailleurs déjà désambiguïser (« Metformine (DFG < 30) », « Metformine (désintensification) »).
Aujourd'hui la condition tombe : 9 profils affichent deux « Sulfamide », 1 profil deux « Glinide ».

**Cet invariant sera ROUGE à l'écriture.** L'écrire en `it.fails`, avec en commentaire le renvoi vers
`plans/P14/S8.md` T-171 qui le lèvera.

### Lire / Modifier

- Modifier : `src/features/decision/engine/banc/paires.test.ts` (créé en T-160).

### Étapes

1. Sur chaque profil figé de chaque nœud : compter les occurrences de chaque `intitule` parmi les
   options `applicable`.
2. Échouer dès qu'un compte dépasse 1, avec un message nommant le nœud, l'intitulé, l'index du profil
   et les **familles** des deux cartes (c'est la famille qui permet de comprendre pourquoi elles
   coexistent).
3. Écrire le test en `it.fails` **et** ajouter juste au-dessus le commentaire expliquant : ce qui est
   attendu, pourquoi c'est rouge aujourd'hui, quelle session le lève.
4. Ajouter un second test qui **prouve que l'invariant sert** (patron I24 / I20) : sur un nœud fabriqué
   à deux options de même intitulé toutes deux applicables, l'invariant mord ; en renommant l'une, il
   passe.

### Validation

- **N0 auto** : `npx vitest run src/features/decision/engine/banc/paires.test.ts` → le `it.fails` est
  compté comme **passé** (il échoue comme attendu) ; le test « preuve que l'invariant sert » est vert.
- **N1 visuel auto** : —
- **N2 humain** : —

### Si bloqué

Si `it.fails` ne se comporte pas comme attendu dans la version de Vitest du dépôt → STOP, ne pas
inventer un `expect(...).rejects` de contournement, signale.

### Message de commit (appliqué en fin de plan)

`test(banc): un écran n'affiche jamais deux cartes de même intitulé (it.fails, P14/S1)`
