`prescription.cible_atteinte` = `position_vs_cible == a_l_objectif OR sous_objectif` (**déclaré**). Dans
une même consultation, un patient à HbA1c 7,4 pour une cible 7 est « non atteinte » d'un côté et peut
être « atteinte » de l'autre. Rien ne le signale : I19/I32 ne couvrent que les critères `partage: true`,
et `cible_atteinte` est un dérivé local des deux côtés.

**Décision référent du 2026-08-06 : la position déclarée par le praticien prime.** C'est donc la
définition de `prescription` qui devient celle du domaine.

## T-181 — Publier la cible, suggérer la position, se taire près des seuils

### Objectif

Livrer la suggestion demandée : la position est **pré-remplie** quand la cible a été déterminée, et
**jamais** quand l'écart est ambigu.

### Décision clé

Le mécanisme est celui de D50 : `cible-glycemique` **publie** la cible que son option retenue porte ;
`HbA1c_cible` la reçoit ; un `preremplissage` de `position_vs_cible` en tire une position. Deux
propriétés non négociables :

- **la position déclarée fait foi** — dès que le praticien touche le champ, le pré-remplissage cesse
  définitivement (sémantique native de `preremplissage`) ;
- **la zone morte** — près des frontières, on ne suggère rien. C'est la réponse à l'objection qui avait
  fait retirer ce mécanisme le 2026-07-29 (« la frontière entre bandes restait discutable près des
  seuils ») : une expression indéterminée ne pré-remplit rien, on s'en sert.

### Lire / Modifier

- Modifier : `content/decision/noeuds/diabete-type-2/cible-glycemique.yaml` (les 4 options),
  `…/prescription.yaml` (`HbA1c_cible` + `preremplissage`), `…/insuline.yaml` (idem)
- Régénérer : les snapshots des trois nœuds

### Étapes

1. Sur chacune des **quatre** options de `cible-glycemique`, déclarer `publie: { critere: HbA1c_cible,
   valeur: … }` avec **le plafond de la carte** (arbitré le 2026-08-06) :

   | Carte | `valeur` |
   | --- | --- |
   | Cible < 9 % | `9` |
   | Cible ≤ 8 % | `8` |
   | Cible ~6,5 % (6,5-7 %) | `7` |
   | Cible ≤ 7 % | `7` |

   Les deux dernières publient le même nombre : c'est voulu, elles diffèrent d'intention et non de
   plafond. **Consigner en commentaire** que le *plancher* de la carte « ~6,5 % » n'est pas
   représentable ainsi — un patient à 6,2 % ne sera pas signalé « sous l'objectif » par ce mécanisme.
2. Déclarer `HbA1c_cible` (`nombre`, `partage: true`, mêmes bornes que dans `insuline`) dans
   `prescription`. Il n'a **qu'un** lecteur : le `preremplissage` ci-dessous — c'est exactement ce que
   le garde-fou de D50 exige.
3. Écrire le `preremplissage` de `position_vs_cible`, **identique dans les deux nœuds**, avec les bandes
   arbitrées le 2026-08-06 — *zone morte autour de l'objectif seulement* :

   | Écart (HbA1c mesurée − cible) | Règle |
   | --- | --- |
   | `< −0,5` | `sous_objectif` |
   | `[−0,5 ; +0,3]` | `a_l_objectif` |
   | `]+0,3 ; +0,5[` | **aucune règle** — le champ reste vide |
   | `[+0,5 ; +1,5]` | `au_dessus` |
   | `> +1,5` | `nettement_au_dessus` |

   Le DSL n'ayant pas de parenthèses, chaque règle s'écrit en conjonction explicite
   (`HbA1c_actuelle > 0 AND HbA1c_cible > 0 AND …`). Exiger les deux valeurs dans **chaque** `quand` :
   sans elles l'expression est indéterminée et rien n'est proposé — le comportement voulu. **Vérifier
   qu'aucune règle ne couvre l'intervalle `]+0,3 ; +0,5[`** : c'est la zone morte, et c'est la réponse
   à l'objection qui avait fait retirer ce mécanisme le 2026-07-29.
4. **Vérifier l'absence de règle « default »** dans ce `preremplissage` : un repli poserait une valeur
   sur un écart ambigu, exactement ce que la zone morte évite.
5. Vérifier le garde-fou de D50 : `HbA1c_cible` n'est cité par aucune `conditions`, `prerequis`,
   `exclusions`, `alertes`, `derive` ni `contraintes` — l'invariant de S10/T-179 étape 6 doit rester vert.
6. `changelog` + `version` des trois nœuds.
